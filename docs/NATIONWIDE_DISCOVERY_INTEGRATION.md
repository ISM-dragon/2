# Nationwide discovery integration report (2026-10-09)

## Existing architecture and conflicts

Latest fetched `origin/main` is `712f9b2`. This session is fixed to `arena/26be0da5-2`, not the requested feature branch. The app uses one Room `AppDatabase`, `PropertyDao`, `PropertyRepository`, `PropertyImportRepository`, provenance/source-link tables, and a canonical identity engine. Discover currently combines **all local properties in memory** with in-memory filters; it does not perform remote nationwide search or paged Room search. `PropertySourceAdapter.fetchProperties` returns a list with a limit, not a continuation token; treating that API as nationwide would lose records. The MLS/wholesale seed adapters return no records. The four portal URL source adapters use synthetic values, not authenticated feeds; URL-intelligence parsers are fixture-tested and are not a licensed listing search API. Existing WorkManager automation is not an authorized listing change feed. Room migrations and underwriting are tightly coupled to canonical rows: provider observations must not be written directly to those rows without a verified mapping and retention policy.

## Implemented boundary

`domain.discovery.ListingProvider` defines search, detail, changes, capabilities, and coverage operations. `ListingDiscovery.page` validates scope and supported filters, performs one bounded request, passes opaque continuation tokens through and deduplicates provider listing IDs within the response. Blank location stays blank and is nationwide only if the provider explicitly advertises nationwide search. State/territory inputs are validated. No provider is registered: the UI explicitly labels its existing results as cached local records, **not live listings**. The contract is deliberately not wired into the old `PropertySourceManager`, since that would falsely imply live licensed inventory. The manual refresh button continues to use existing sources (currently empty); it is not a nationwide feed.

## Blockers and production integration plan

No verified licensed API, credentials, coverage specification, pagination schema, quota, sync cursor, removal semantics, or caching permission exists in this repository. A provider requiring a secret needs a separately reviewed trusted service; do not ship keys in the APK. Until a provider contract and deployment are approved, nationwide results, incremental sync, WorkManager refresh, per-provider checkpoints, persistence of observations, offline freshness guarantees, and complete coverage **cannot** be promised. Before enabling one: implement a licensed adapter against verified documentation; query paged results into existing Room via the transactional importer with a unique provider-listing constraint and migration tests; persist scope-bound checkpoints in the same transaction as observations; use unique WorkManager work with network constraints/backoff; show timestamps and partial coverage from actual feed metadata; verify rate limits, retention, and deletion policy. Avoid running state fan-out for a provider without documented regional coverage. Preserve canonical/financial records when sources fail. Do not interpret `scannedAt` as provider verification time.

The existing custom-property form also previously generated randomized Austin coordinates for manually entered addresses. Those coordinates have been changed to zero as an explicit unknown sentinel; map consumers must suppress unknown coordinates before map display in a production geocoding integration. Other generated underwriting defaults in that form remain existing technical debt, not provider listing data.
